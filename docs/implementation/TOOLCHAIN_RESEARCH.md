## Compatibility choices

AGP 9.4 requires Gradle >=9.6, JDK >=17, and supports compile SDK 37. The current baseline already passes assemble, unit tests and lint on Gradle 9.8/JBR 25. Java source/bytecode can remain targeted below the build JDK; target Java 17 consistently for application code.

Keep AGP's built-in Kotlin support. Do not apply `org.jetbrains.kotlin.android`. The published AGP 9.4.1 POM still brings KGP 2.2.10; explicitly upgrade the top-level buildscript's `org.jetbrains.kotlin:kotlin-gradle-plugin` dependency to 2.4.20, and align Compose/serialization plugins. This follows the [official built-in Kotlin upgrade instructions](https://developer.android.com/build/releases/agp-9-0-0-release-notes#upgrade_to_a_higher_kgp_version). Supabase 3.8.0 itself is compiled with Kotlin 2.4.0, so retaining Kotlin 2.2.10 is inappropriate.

KGP 2.4.20's fully tested table currently ends at AGP 9.3.1 / Gradle 9.7.0. Kotlin documentation explicitly permits the newest releases beyond that range with possible warnings. Retain the newer stable AGP/Gradle already present, then verify the upgraded compiler with the actual build. A tested build is required before claiming this entire selected combination works. Material/Compose preview compatibility is recorded separately in the design research.

## Architecture and navigation

Follow [Android architecture recommendations](https://developer.android.com/topic/architecture/recommendations): single activity, repository boundaries, `ViewModel` immutable `StateFlow` state, `viewModelScope`, lifecycle-aware `collectAsStateWithLifecycle`, constructor injection through a small app dependency container. Keep domain arithmetic and time classification pure; use `java.time` supported by the existing minimum SDK.

[Navigation 3](https://developer.android.com/guide/navigation/navigation-3) is now the recommended Compose navigation solution. Use serializable keys with `rememberNavBackStack`, `entryProvider` and `NavDisplay`; top-level tabs and selected-date day screens should restore state. Navigation 3 stable 1.2.0 is preferable to its 1.3 alpha for this task. Lifecycle provides `lifecycle-viewmodel-navigation3` if entry-scoped ViewModels become necessary.

## Supabase Kotlin and existing-account email/password

Install `Auth` and `Postgrest` using Supabase's BOM and provide the official Ktor `ktor-client-okhttp` engine. Align Ktor's client dependencies to 3.6.0; upstream Supabase 3.8.0's [version catalog](https://github.com/supabase-community/supabase-kt/blob/3.8.0/gradle/libs.versions.toml) was built with Ktor 3.5.1, coroutines 1.11.0 and serialization 1.11.0, making Ktor's minor upgrade a verification point.

JetMeal explicitly selects `OkHttp.create()` rather than relying on engine discovery. The [Ktor 3.6 engine guide](https://ktor.io/docs/client-engines.html) officially supports both Android and OkHttp engines for Android. The Android platform engine was evaluated after a native HTTPS probe succeeded, and its real physical-phone anonymous SDK read passed. However, activity/ViewModel cancellation then raised an uncaught `CompletionHandlerException` while closing a gzip/chunked response: the platform HTTP implementation reported `IllegalStateException: Unbalanced enter/exit` through Ktor's `RawSourceChannel.close`. That observed failure led back to OkHttp, retaining the explicit request timeouts and disabled PostgREST retries. No TLS validation bypass or custom insecure transport is used. The earlier headless initialization wait was separate from engine networking, as recorded below.

The product owner's 2026-10-06 decision replaces the earlier OTP screen with existing-account email/password login. The current [Kotlin password sign-in reference](https://supabase.com/docs/reference/kotlin/auth-signinwithpassword) and pinned [Email provider](https://github.com/supabase-community/supabase-kt/blob/3.8.0/Auth/src/commonMain/kotlin/io/github/jan/supabase/auth/providers/builtin/Email.kt) specify:

```kotlin
supabase.auth.signInWith(Email) {
    email = address
    password = enteredPassword
}
```

The [password Auth guide](https://supabase.com/docs/guides/auth/passwords) documents the existing-account grant. JetMeal sends the exact entered password, normalizes email only, and has no runtime signup/reset/OTP flow. Real local tests may provision an account through `signUpWith(Email)` and Mailpit confirmation, then sign out before the UI password login. The separate RLS integration test retains direct SDK `signInWith(OTP)`/`verifyEmailOtp` solely for local independent-user setup. Those SDK APIs are absent from production.

The password field uses current Material 3 `OutlinedSecureTextField`, checked against the downloaded 1.5.0-alpha29 `SecureTextField.kt` source. Its `TextFieldState` is constructed with plain `remember` (the convenience `rememberTextFieldState` saves state and is deliberately unsuitable here). `TextObfuscationMode.Hidden` masks every character; the secure component disables clipboard copying and uses password keyboard options. Button and `onKeyboardAction` submissions share validation and the busy guard. No input transformation trims or modifies the password.

The pinned [AuthConfig source](https://github.com/supabase-community/supabase-kt/blob/3.8.0/Auth/src/commonMain/kotlin/io/github/jan/supabase/auth/AuthConfig.kt) confirms `autoLoadFromStorage`, `autoSaveToStorage`, `alwaysAutoRefresh` and Android `enableLifecycleCallbacks` default to true. Observe `auth.sessionStatus`, await initialization before loading user data, and handle `Initializing`, `Authenticated`, `NotAuthenticated` and `RefreshFailure`. Use `auth.events` for refresh-failure diagnostics; `SessionStatus.RefreshFailure.cause` is deprecated. Android foreground/background hooks already pause/resume refresh.

Network timeout behavior was verified against downloaded 3.8.0 sources. [SupabaseClientBuilder](https://github.com/supabase-community/supabase-kt/blob/3.8.0/Supabase/src/commonMain/kotlin/io/github/jan/supabase/SupabaseClientBuilder.kt) defaults the core request timeout to 10 seconds, but [Postgrest.Config](https://github.com/supabase-community/supabase-kt/blob/3.8.0/Postgrest/src/commonMain/kotlin/io/github/jan/supabase/postgrest/Postgrest.kt) independently overrides it to 30 seconds and enables 3 retries. [RestRequestExecutor](https://github.com/supabase-community/supabase-kt/blob/3.8.0/Postgrest/src/commonMain/kotlin/io/github/jan/supabase/postgrest/executor/RestRequestExecutor.kt) retries GET/HEAD only for HTTP 503/520 or wrapped `HttpRequestException`, with 1/2/4-second backoff; authorization 401/403 and `HttpRequestTimeoutException` are not retried. JetMeal explicitly sets core/Auth and PostgREST request timeouts to 15 seconds and disables PostgREST retries for foreground responsiveness. This bounds the individual HTTP request rather than promising an entire multi-request refresh completes in 15 seconds. Auth's normal background session-refresh retry remains enabled. A long cloud test alone does not prove the SDK or backend was its cause; distinguish raw Android connectivity, response handling and initialization in real instrumentation.

A concrete initialization wait was then found in the headless cloud-test setup: [AuthImpl](https://github.com/supabase-community/supabase-kt/blob/3.8.0/Auth/src/commonMain/kotlin/io/github/jan/supabase/auth/AuthImpl.kt) loads an empty session but retains `Initializing`. Android [setupPlatform](https://github.com/supabase-community/supabase-kt/blob/3.8.0/Auth/src/androidMain/kotlin/io/github/jan/supabase/auth/setupPlatform.kt) normally calls `initDone` from the process lifecycle's `onStart`. Without an Activity that event may never occur, so `awaitInitialization()` blocks before an HTTP request and network timeouts do not apply. Headless test clients must set the public `enableLifecycleCallbacks = false`; this path directly calls `initDone`. The local two-user repository test already uses that setting. Production has a real MainActivity and retains default lifecycle callbacks. This evidence does not establish an HTTP engine defect.

Refresh/search jobs also guard publication with coroutine `ensureActive` and a generation counter. A superseded job cannot publish stale data, clear the current job's progress, or turn a cancellation-related I/O exception into a connection banner. Sign-out invalidates outstanding read generations and resets their progress. The real local E2E test now repeatedly refreshes, navigates and replaces searches, then checks the latest destination/catalogue and absence of a spurious error; its execution must be recorded separately from the implementation.

The [SessionManager interface](https://github.com/supabase-community/supabase-kt/blob/3.8.0/Auth/src/commonMain/kotlin/io/github/jan/supabase/auth/SessionManager.kt) supports a platform secure implementation (`saveSession`, `loadSession`, `deleteSession`). Keep token persistence private and out of backups and logs; app config contains only project URL and publishable key. Clear user-specific UI data when auth state changes. Real password/session/RLS verification requires the reachable Supabase infrastructure checked in preflight.

Session storage was checked against the downloaded 3.8.0 source artifact for the local-to-hosted rollout. [SettingsUtil](https://github.com/supabase-community/supabase-kt/blob/3.8.0/Auth/src/settingsMain/kotlin/io/github/jan/supabase/auth/SettingsUtil.kt) scopes its default key to the URL. However, [SettingsSessionManager](https://github.com/supabase-community/supabase-kt/blob/3.8.0/Auth/src/settingsMain/kotlin/io/github/jan/supabase/auth/SettingsSessionManager.kt) automatically migrates a legacy unscoped `session` into a new project key. JetMeal therefore supplies the official manager with a private SharedPreferences file named by a stable SHA-256 digest of the canonical project endpoint. The manager uses its default key inside that isolated file, avoiding the legacy migration. Local and hosted accounts cannot reuse one another's sessions; future app updates and publishable-key rotations retain the current project's session. Existing unscoped SDK preferences remain untouched and are not imported. Android backup and device-transfer exclusions cover every preference file.

[Auth error codes](https://supabase.com/docs/guides/auth/debugging/error-codes) and the pinned [AuthRestException](https://github.com/supabase-community/supabase-kt/blob/3.8.0/Auth/src/commonMain/kotlin/io/github/jan/supabase/auth/exception/AuthRestException.kt) provide structured classification. JetMeal maps rejected credentials, unconfirmed email, request rate limits, disabled email sign-in and invalid sessions to fixed user guidance. The rejected-credential message does not disclose whether the email exists or password was wrong. Unknown server responses, exception descriptions, addresses, passwords and tokens never become UI messages. Connectivity errors have distinct guidance; for data operations it asks the user to refresh before repeating a write whose response may have been lost.

Before the password-login change, the earlier Auth-message/session-storage change was verified on 2026-10-06 with `:app:testDebugUnitTest :app:assembleDebug :app:lintDebug`, using the ignored hosted client configuration and Android Studio JBR. All 32 unit tests passed (20 domain, 8 error classification, 4 endpoint isolation), and the debug APK/lint tasks succeeded. That historical run did not verify the subsequent password UI, hosted Auth, device session persistence, or local Mailpit instrumentation; those paths require separate real integration verification.

The skill-required `https://supabase.com/changelog.md` check was attempted through browsing and direct HTTPS; the endpoint failed (transport connection closed). Current task-specific official documentation, client release notes and source were reachable, so that index failure does not prevent current API research.

## SDK date-range serialization workaround

Real Android end-to-end testing exposed a Supabase Kotlin 3.8.0 query issue: two top-level filters on the same column retain both values in the filter builder, but [PostgrestRequestBuilder](https://github.com/supabase-community/supabase-kt/blob/3.8.0/Postgrest/src/commonMain/kotlin/io/github/jan/supabase/postgrest/query/PostgrestRequestBuilder.kt) serializes them through `params.mapToFirstValue()`. A `gte` followed by `lt` therefore loses the upper bound. Use a single explicit `and { gte(...); lt(...) }` logical expression for date ranges. The [logical formatter](https://github.com/supabase-community/supabase-kt/blob/3.8.0/Postgrest/src/commonMain/kotlin/io/github/jan/supabase/postgrest/query/filter/PostgrestFilterBuilder.kt) includes every value inside that one parameter. Keep the real integration regression checking both adjacent local dates have exactly their own entries.
